# Партнёрские предложения Яндекс Маркета: production-контур

Дата актуализации: **30 июля 2026 года**.

KREPI TV остаётся полезным без коммерческого слоя: характеристики, расчёт
совместимости и взаимные страницы телевизоров и кронштейнов существуют
независимо от Маркета. Партнёрская кнопка появляется только у свежей, точно
привязанной и промаркированной карточки.

## Что реализовано

- `data/affiliate/market-products.json` — публичный манифест известных карточек
  Маркета; сейчас пуст, реальные URL не выдумываются;
- `scripts/affiliate/check-market-links.mjs` — приватный запрос к официальному
  `GET /partner/link/create`;
- `scripts/affiliate/build-snapshot.mjs` — fail-closed решение о публикации;
- `scripts/affiliate/publish-snapshot.mjs` — единственный разрешённый путь из
  `.private/` в `data/affiliate/public-offers.json`;
- `AffiliateOffer` — прямой переход на `market.yandex.ru`, фото и заголовок из
  API, видимая маркировка и атрибуция;
- `.github/workflows/affiliate-health.yml` — две проверки в сутки без
  постоянного сервера, три повтора при технической ошибке и ручной запуск;
- JSON Schema, исполняемые валидаторы и негативные тесты.

В браузер, `docs/`, git и логи не попадают OAuth, заголовки авторизации, сырые
ответы ошибок и содержимое `.private/`.

## Точная привязка товара

Каждая запись манифеста относится только к кронштейну и содержит:

- `entity_kind: "mount"`;
- `entity_id`, совпадающий с каталогом;
- точный `page_path: /kronshteyny/{entity_id}/`;
- `expected_title_tokens` — точные бренд и модель из `data/mounts.json`,
  например `iTECHmount` и `SLT-460`;
- канонический URL карточки Маркета без реферальных параметров;
- стабильный VID и зарегистрированный ERID.

До сетевого запроса валидатор сверяет `entity_id` с реальным кронштейном
каталога и требует точные `brand` и `model` среди identity-токенов. Checker
принимает только `pageName=POKUPKI_PRODUCT` и заголовок, содержащий все токены
как отдельные нормализованные слова. `SLT-460X` не считается совпадением для
`SLT-460`. Карточка другого товара получает `wrong_product`, а CTA не
публикуется. Похожая модель никогда не подставляется автоматически.

## Когда оффер публикуется

Одновременно должны выполняться все условия:

- API вернул корректную карточку товара;
- хост ссылки — ровно `market.yandex.ru`;
- хост фото — ровно `avatars.mds.yandex.net`;
- идентичность страницы и модели совпала с манифестом;
- `promise > 0` и `stockAmount > 0`;
- креатив имеет ERID и дату регистрации;
- ERID в прямой ссылке совпадает с креативом;
- снимок не старше 48 часов.

Иначе `affiliate_href` удаляется из публичного снимка. Страница, источники и
совместимость остаются доступны. На одной странице допустимо несколько офферов
одного физического кронштейна: клиент выбирает первый свежий допустимый вариант.

Публичная ссылка всегда имеет
`rel="sponsored nofollow noopener noreferrer"`. `/go/`, собственных редиректов,
сторонних сокращателей, JavaScript-подмены и отдельной выдачи роботам нет.

## Статусы и отказоустойчивость

- HTTP `404/410` — `unavailable`, CTA снимается;
- неверная физическая модель — `wrong_product`, CTA снимается;
- нулевое вознаграждение — `no_reward`, CTA снимается;
- нулевой остаток — `out_of_stock`, CTA снимается;
- timeout, `429`, `5xx`, невалидный JSON или общий API error — технический
  `error`.

Каждая карточка получает до трёх персональных попыток. Если после них остаётся
`error`, обновление остальных карточек не блокируется: для сломанной записи
сохраняется только её собственный last-known-good, если он относится к тому же
товару, креативу и не старше 48 часов. Устаревшая запись отбрасывается. Workflow
после безопасной публикации здоровых карточек всё равно завершается ошибкой,
чтобы технический отказ не остался без уведомления.

После изменения workflow коммитит только два проверенных публичных файла с
`[skip ci]`, затем явно вызывает официальный endpoint GitHub Pages
`POST /repos/{owner}/{repo}/pages/builds`. Это нужно потому, что push с
`GITHUB_TOKEN` сам по себе не запускает Pages build. Job ждёт завершения Pages
для точного коммита и сравнивает SHA-256 production JSON с собранным файлом.

## Настройка перед первым реальным оффером

1. Площадка `krepitv.ru` должна быть одобрена в программе Маркета.
2. Вручную выбрать карточку именно нужной модели кронштейна с реферальной
   наградой.
3. Зарегистрировать фактический рекламный креатив и получить ERID.
4. Добавить карточку в `market-products.json`, включая точный `entity_id` и
   модель в `expected_title_tokens`.
5. В GitHub Actions создать secret `YANDEX_MARKET_AFFILIATE_OAUTH` и repository
   variable `YANDEX_MARKET_PLACE_ID`.
6. Запустить workflow вручную и проверить один полный цикл до массового
   наполнения.

Локальный эквивалент:

```bash
YANDEX_MARKET_AFFILIATE_OAUTH=... \
YANDEX_MARKET_PLACE_ID=... \
npm run affiliate:check-market
npm run affiliate:build-snapshot
npm run affiliate:publish-snapshot
npm run build
```

## Фото и данные Маркета

Точное фото изделия выводится только из `productPhoto` авторизованного API или
из отдельного медиакаталога с зафиксированным правом использования. Фото
производителей и магазинов не копируются вслепую. При ошибке загрузки внешний
снимок скрывается без поддельной заглушки.

Рядом с API-заголовком и фото показываются пометка «Реклама», рекламодатель,
ИНН, ERID и ссылка «Данные сервиса Яндекс Маркет». Цена намеренно не копируется:
кнопка говорит «Проверить цену на Яндекс Маркете», где учитывается регион.

## Проверки

```bash
npm run affiliate:validate
npm run affiliate:validate-public
npm run affiliate:test
npm run build
```

Production-валидатор принимает только реальные хосты Яндекса. Режим
`example.invalid` разрешён исключительно для файлов в `tests/fixtures/`.
