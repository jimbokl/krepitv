# Партнёрские предложения Яндекс Маркета: production-контур

Дата актуализации: **31 июля 2026 года**.

KREPI TV остаётся полезным без коммерческого слоя: характеристики, расчёт
совместимости и взаимные страницы телевизоров и кронштейнов существуют
независимо от Маркета. Партнёрская кнопка появляется только у свежей, точно
привязанной и промаркированной карточки.

## Что реализовано

- `data/affiliate/market-products.json` — публичный манифест 17 известных
  карточек кронштейнов Маркета;
- `scripts/affiliate/check-market-links.mjs` — приватный запрос к официальному
  `GET /partner/link/create`;
- `scripts/affiliate/check-market-links-chrome.mjs` — тот же запрос через уже
  открытый внешний Chrome, когда терминальный маршрут блокируется Яндексом;
- `scripts/affiliate/build-snapshot.mjs` — fail-closed решение о публикации;
- `scripts/affiliate/publish-snapshot.mjs` — единственный разрешённый путь из
  `.private/` в `data/affiliate/public-offers.json`; он отбрасывает все
  недопущенные офферы и удаляет `promise`, `price` и `stock`;
- `AffiliateOffer` — прямой переход на `market.yandex.ru`, фото и заголовок из
  API, обязательная маркировка рекламного режима и атрибуция;
- статический HTML содержит только нейтральный `data-affiliate-slot` без
  `href`; клиент загружает снимок только с собственного origin без кеша и
  показывает кнопку после повторной проверки снимка и оффера;
- `.github/workflows/affiliate-health.yml` — ручной CI-прогон. Расписание
  отключено до подтверждения, что GitHub runner не получает VPN-блок;
- JSON Schema, исполняемые валидаторы и негативные тесты.

В браузер, `docs/`, git и логи не попадают OAuth, заголовки авторизации, сырые
ответы ошибок, числовые цена/остаток/вознаграждение и содержимое `.private/`.

## Точная привязка товара

Каждая запись манифеста относится только к кронштейну и содержит:

- `entity_kind: "mount"`;
- `entity_id`, совпадающий с каталогом;
- точный `page_path: /kronshteyny/{entity_id}/`;
- `expected_title_tokens` — точные бренд и модель из `data/mounts.json`,
  например `iTECHmount` и `SLT-460`;
- канонический URL карточки Маркета без реферальных параметров;
- явный `compliance_mode`, CLID и стабильный VID;
- для рекламы — зарегистрированный ERID и реквизиты креатива;
- для товарной витрины — `creative: null`, совпадающий CLID и отсутствие ERID.

До сетевого запроса валидатор сверяет `entity_id` с реальным кронштейном
каталога и требует точные `brand` и `model` среди identity-токенов. Checker
принимает только `pageName=POKUPKI_PRODUCT` и заголовок, содержащий все токены
как отдельные нормализованные слова. `SLT-460X` не считается совпадением для
`SLT-460`. Карточка другого товара получает `wrong_product`, а CTA не
публикуется. Похожая модель никогда не подставляется автоматически.

## Когда оффер публикуется

Одновременно должны выполняться общие условия:

- API вернул корректную карточку товара;
- хост ссылки — ровно `market.yandex.ru`;
- хост фото — ровно `avatars.mds.yandex.net`;
- идентичность страницы и модели совпала с манифестом;
- `promise > 0` и `stockAmount > 0`;
- CLID и VID в прямой ссылке совпадают с манифестом;
- публичный снимок и сам оффер не старше 48 часов.

Для `advertising` дополнительно обязательны ERID, дата регистрации и полная
маркировка. Для явно классифицированного `non_ad_storefront` объект `creative`
обязан быть `null`, а ERID запрещён. Необязательный длинный партнёрский
дисклеймер в этом режиме не выводится. Режим не выводится автоматически из
вида ссылки.

Иначе весь оффер отсутствует в публичном снимке. Страница, источники и
совместимость остаются доступны. На одной странице допустимо несколько офферов
одного физического кронштейна: клиент выбирает первый свежий допустимый вариант.

Публичная ссылка всегда имеет
`rel="sponsored nofollow noopener noreferrer"`. `/go/`, собственных редиректов,
сторонних сокращателей и отдельной выдачи роботам нет. Клиентская активация
ссылки служит fail-closed проверкой свежести: URL берётся из того же публичного
снимка, который проходит серверную сборку, и не меняет назначение ссылки.

## Статусы и отказоустойчивость

- HTTP `404/410` — `unavailable`, CTA снимается;
- неверная физическая модель — `wrong_product`, CTA снимается;
- нулевое вознаграждение — `no_reward`, CTA снимается;
- нулевой остаток — `out_of_stock`, CTA снимается;
- timeout, `429`, `5xx`, невалидный JSON или общий API error — технический
  `error`.

Каждая карточка получает до трёх персональных попыток. Если после них остаётся
`error`, обновление остальных карточек не блокируется, а сломанная запись
снимается по строгому fail-closed правилу. Публичный снимок не используется как
хранилище last-known-good: в нём намеренно нет приватных входов решения.
Workflow после безопасной публикации здоровых карточек всё равно завершается
ошибкой, чтобы технический отказ не остался без уведомления.

После получения нового снимка workflow устанавливает зафиксированные Node-
зависимости, Rust 1.93.1, WASM target и `wasm-pack` 0.13.1, затем запускает полный
`npm run build`. Поэтому партнёрские карточки проходят не только JSON-
валидацию: в предрендеренные HTML-страницы до коммита попадает только безопасный
placeholder без URL, а действующая кнопка создаётся клиентом после повторной
проверки same-origin снимка. Workflow
добавляет только проверенные публичные артефакты (`public-offers.json`,
`docs/` и отслеживаемые промежуточные public-файлы), а изменение любого другого
tracked-файла останавливает публикацию.

Проверенный build коммитится с `[skip ci]`, после чего workflow явно вызывает
официальный endpoint GitHub Pages `POST /repos/{owner}/{repo}/pages/builds`.
Это нужно потому, что push с `GITHUB_TOKEN` сам по себе не запускает Pages
build. Job ждёт сборку точного коммита, затем побайтово сравнивает с production
публичный JSON и статическую страницу каждого опубликованного кронштейна.

## Настройка перед первым реальным оффером

1. Площадка `krepitv.ru` должна быть одобрена в программе Маркета.
2. Вручную выбрать карточку именно нужной модели кронштейна с реферальной
   наградой.
3. Явно зафиксировать режим: рекламный креатив с ERID либо товарная витрина без
   ERID согласно подтверждённому сценарию размещения.
4. Добавить карточку в `market-products.json`, включая точный `entity_id` и
   модель в `expected_title_tokens`.
5. Для CI создать secret `YANDEX_MARKET_AFFILIATE_OAUTH`, затем вручную
   проверить доступность API с GitHub runner до включения расписания.

Локальный эквивалент:

```bash
npm run affiliate:check-market-chrome
npm run affiliate:build-snapshot
npm run affiliate:publish-snapshot
npm run build
```

## Фото и данные Маркета

Точное фото изделия выводится только из `productPhoto` авторизованного API или
из отдельного медиакаталога с зафиксированным правом использования. Фото
производителей и магазинов не копируются вслепую. При ошибке загрузки внешний
снимок скрывается без поддельной заглушки.

В рекламном режиме рядом с API-заголовком и фото показываются пометка
«Реклама», рекламодатель, ИНН и ERID. В режиме товарной витрины необязательный
партнёрский дисклеймер не показывается.
Цена и численный остаток намеренно не выводятся: кнопка говорит «Проверить цену
на Яндекс Маркете», где учитывается регион пользователя. Значения `promise`,
`price` и `stock` существуют только в `.private/market-affiliate-batch.json` и
`.private/market-affiliate-snapshot.json`. Отдельная публичная схема запрещает
эти ключи в `data/` и `docs/data/`.

## Проверки

```bash
npm run affiliate:validate
npm run affiliate:validate-public
npm run affiliate:test
npm run build
```

Production-валидатор принимает только реальные хосты Яндекса. Режим
`example.invalid` разрешён исключительно для файлов в `tests/fixtures/`.
