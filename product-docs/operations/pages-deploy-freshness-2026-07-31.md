# GitHub Pages без ложного обновления всего сайта

Дата решения: 31 июля 2026 года.

Актуализировано 2 августа 2026 года: после обнаружения межплатформенной разницы
WASM production-сборка перенесена в закреплённый Ubuntu runner. Ограничение
ложных деплоев сохранено через список production-relevant paths.

## Проблема

GitHub Pages был настроен как legacy source `main:/docs`. Из-за этого любой
служебный коммит в `main` повторно публиковал неизменённый `docs/` и обновлял
HTTP `Last-Modified` сразу у всех 142 URL. Содержимое страниц не менялось, но
поисковому роботу приходилось заново проверять свежесть всего сайта.

Это не доказанная причина текущей медленной индексации: Google успел обойти
только девять URL, восемь из них уже в PASS. Исправление убирает единственный
обнаруженный системный источник ложной свежести.

## Новый контракт

- Pages использует custom GitHub Actions workflow;
- обычный push запускает публикацию только при изменении исходников,
  production-данных, сборочного контура или `docs/**`;
- ручной `workflow_dispatch` оставлен для безопасного восстановления;
- read-only build job выполняет полный закреплённый `npm run build` и загружает
  созданный им `docs/`;
- отдельный deploy job получает write-права Pages только после успешной сборки;
- WASM дважды воспроизводится на одном runner и публикуется из этой же сборки,
  поэтому локальная разница macOS/Linux не оставляет в production старый бинарь;
- все remote actions закреплены полными commit SHA;
- affiliate health публикует artifact напрямую только когда проверенный public
  snapshot действительно изменился;
- аналитика, исследования и документация больше не должны менять
  `Last-Modified` production.

После переключения `build_type` на `workflow` требуется один контрольный
деплой, затем HTTPS smoke и побайтовая сверка production sitemap с локальным.
