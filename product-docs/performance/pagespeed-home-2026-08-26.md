# KREPI TV — разбор PageSpeed главной страницы

**Дата исходного отчёта:** 2026-08-26 08:06:54

**URL:** `https://krepitv.ru/`

**Режим:** mobile lab, Lighthouse 13.4.1, Moto G Power, slow 4G
**Статус полевых данных:** отсутствуют; выводы относятся к лабораторному запуску и воспроизведению через headless Chrome.

## Вердикт

Сайт не «тормозит от тяжёлого JavaScript». `TBT=0 мс`, `FCP=1,4 с`, accessibility/best-practices/SEO дают 100. Главный дефект — поздняя полная замена полезного SSR другой React-разметкой после загрузки общего каталога. Она создаёт `CLS=0,302` и повторно определяет LCP. Веб-шрифты дают второй, меньший сдвиг.

`Performance=73` — ориентир одного лабораторного запуска, не полевой рейтинг сайта и не доказательство потери позиций. Но `CLS=0,302` уже находится в плохом диапазоне, а `LCP=3,8 с` требует улучшения. Это P0 следующего спринта, потому что дефект затрагивает первый экран и путь к конверсии.

## Подтверждённая причина CLS

Текущий bootstrap:

1. Rust sitegen отдаёт полезный статический homepage SSR.
2. `main.jsx` загружает route module.
3. `loadCatalog()` ждёт общий `Promise.all` всех обязательных данных.
4. `createRoot(rootElement).render(...)` очищает существующий SSR.
5. React вставляет другую по структуре и высоте homepage-разметку.

В воспроизведении Chrome с mobile viewport, CPU ×4 и slow 4G:

| Момент | Состояние `#root` | `main.top` | `root.height` |
|---|---|---:|---:|
| DOMContentLoaded | SSR, первым элементом `<header>` | 142 px | 4 134,7 px |
| после загрузки шрифтов | SSR | 142 px | 4 110,7 px |
| начало `createRoot` | root временно пуст | — | 0 px |
| React render | первым элементом `<main>` | 0 px | 4 801,8 px |

Пустой промежуток длился около 300 мс. Главный заголовок удаляется и вставляется заново, поэтому браузер может выбрать новый LCP-кандидат спустя несколько секунд после первого полезного HTML.

Это архитектурный дефект progressive enhancement: SSR используется как временная заставка, а не как стабильная основа интерактива.

## Почему замена происходит поздно

Главная страница ждёт данные, большая часть которых не нужна для первого экрана:

- `tv-models.json`;
- `market-tv-models.json`;
- `mounts.json`;
- `model-search.json`;
- `seo-pages.json`;
- `compatibility-graph.json`;
- `commercial-profiles.json`;
- три installation-kit справочника;
- два affiliate snapshot.

Самый крупный запрос отчёта — `seo-pages.json`, около 117 КиБ transfer. Общая загрузка данных становится барьером до React render. Базовые affiliate snapshots также запрашиваются на главной до появления интерактива, хотя не участвуют в первом пользовательском действии.

## Веб-шрифты

Глобальный entry импортирует шесть начертаний:

- Roboto Condensed 700 и 800;
- IBM Plex Sans 400, 500 и 600;
- IBM Plex Mono 400.

`@fontsource` генерирует отдельные `@font-face` по subset, все с `font-display: swap`. Для русского первого экрана браузер загрузил cyrillic и latin-файлы нескольких начертаний. PageSpeed назвал шрифты источниками layout shift; в воспроизведении они изменили высоту SSR примерно на 24 px ещё до React replacement.

Шрифты — реальная, но вторичная причина. Сначала нужно убрать разрушительную замену root, затем повторно измерить остаточный CLS и только после этого выбирать preload/variable subset/metric-compatible fallback.

## Вторичные предупреждения

### Cache TTL 10 минут

Production на GitHub Pages возвращает `Cache-Control: max-age=600` и для HTML, и для hashed assets. Это объясняет рекомендацию PageSpeed примерно на 297 КиБ повторной загрузки. На GitHub Pages заголовок нельзя настроить проектным `_headers`.

Это не причина CLS и не главный источник LCP первого визита. Перенос или CDN-прокси только ради оценки PageSpeed сейчас не оправдан. После исправления P0 можно отдельно сравнить бесплатный Cloudflare CDN/Pages, не затрагивая Cloud.ru.

### Render-blocking CSS

Один CSS-файл около 21 КиБ даёт оценочную экономию 300 мс; Lighthouse считает примерно 17 КиБ неиспользуемыми на главной. Это следствие общего Tailwind bundle для многих route components. Оптимизация полезна после стабилизации SSR, но не должна предшествовать исправлению CLS.

### Unused JavaScript

Около 31 КиБ из transfer основного JS не используется в первом экране. Route chunking уже есть, но общий bootstrap, React runtime, каталог и общие компоненты всё ещё загружаются. `TBT=0` показывает, что это сетевой, а не CPU-дефект.

### Preconnect

Все критические запросы идут с `krepitv.ru`; PageSpeed не нашёл полезного дополнительного origin. Добавлять preconnect некуда.

## Выбранное исправление

### 1. Стабильный SSR и интерактивные islands

На главной не заменять весь `#root`. Сохранить Rust SSR как финальную структуру и монтировать React только в заранее зарезервированный search island. SSR и island должны иметь одинаковую минимальную геометрию, чтобы загрузка интерактива не двигала соседние блоки.

Не применять `hydrateRoot` к несовпадающей разметке: это лишь заменит явное очищение hydration mismatch и не устранит причину.

После homepage проверить тем же инструментом одну модельную страницу и `/podbor/`. Если полный root replacement воспроизводится там, мигрировать только нужные интерактивные области, начиная с коммерческой когорты.

### 2. Route-scoped data loading

Первый интерактив главной требует только компактный `model-search.json`. Паспортные данные, граф, installation-kit справочники и affiliate snapshots загружаются только на соответствующем route или после явного действия пользователя.

### 3. Шрифты после архитектурного фикса

Сначала повторно измерить. Если CLS остаётся выше 0,1:

- оставить только реально используемые веса первого экрана;
- рассмотреть variable font или ручные cyrillic/latin subsets;
- preload не более критических файлов;
- использовать `font-display: optional` либо metric-compatible fallback, проверив визуальный reference на slow network.

### 4. CSS/JS и CDN только затем

Critical CSS, route-level Tailwind и CDN cache — отдельные измеримые оптимизации. Каждая применяется по одной и сравнивается с одним baseline, чтобы не потерять причинность.

## Performance budget спринта

Лабораторный gate запускается минимум три раза на homepage, treatment model page и `/podbor/`. Для gate используется медиана завершённых запусков в одинаковом профиле.

| Метрика | Gate |
|---|---:|
| CLS | ≤ 0,10; целевой ≤ 0,05 |
| LCP mobile lab | ≤ 2,5 с |
| TBT | ≤ 200 мс |
| FCP | не ухудшить более чем на 0,2 с от baseline |
| временно пустой `#root` | 0 событий |
| full-root replacement после FCP | запрещён |
| новые индексируемые URL | 0 |

Если LCP остаётся выше 2,5 с после устранения root replacement, следующая одиночная гипотеза — шрифты. Если после шрифтов проблема сохраняется, исследуются critical CSS и сетевой waterfall. Несколько исправлений не смешиваются в одном измерении.

## Влияние на SEO

Core Web Vitals входят в набор page-experience сигналов, но идеальная оценка PageSpeed не гарантирует высоких позиций. Поэтому исправляется конкретный пользовательский дефект — прыгающий первый экран — без переписывания контента или массового создания страниц.

Полевой результат оценивается позже по 75-му процентилю mobile/desktop в Search Console или CrUX, когда появится достаточный объём данных. До этого лабораторный gate предотвращает регрессию, но не выдаётся за полевой Core Web Vitals статус.
